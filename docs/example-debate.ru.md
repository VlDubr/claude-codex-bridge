# Настоящий спор, от начала до конца

**Русский** · [English](example-debate.md)

Это не постановочное демо. Это обмен репликами, который произошёл в этом
репозитории 27 августа 2026 года, пока чинился тест, падавший на CI со дня
своего появления. Заканчивается он коммитом
[`cc2f8a1`](https://github.com/VlDubr/tandem/commit/cc2f8a1).

Реплики приведены в оригинале, вывод команд — дословно.

---

## Обстановка

`scripts/codex-core.mjs` один раз опрашивает локальный бинарь `codex` и
запоминает, какие флаги принимает его подкоманда `exec`:

```js
let capsCache = null;
export function capabilities({ force = false } = {}) {
  if (capsCache && !force) return capsCache;
  ...
  return (capsCache = caps);
}
```

Тест, утверждавший, что `--ask-for-approval` доходит до генерации изображений,
не проходил на Linux никогда. Причина — кэш модулей: тесты обходят его через
`import("./image-core.mjs?caps4=" + Date.now())`, но это создаёт новый экземпляр
только самого `image-core`. Его статический `import "./codex-core.mjs"`
разрешается в один и тот же URL, поэтому `capsCache` общий на весь прогон.
Проба выполнялась в более раннем тесте, а этот получал её результат.

В тестах починено, CI зелёный. Оставался вопрос: заслуживает ли правки сам
продуктовый код.

## Позиция Claude

> Продуктовый код трогать не нужно. Модульный синглтон здесь уместен:
>
> 1. `capabilities()` делает два синхронных `spawnSync` в главном процессе
>    MCP-сервера. Кэш нужен именно чтобы не платить за это на каждый вызов.
> 2. В продакшене процесс живёт с одним бинарём codex; смена бинаря в середине
>    жизни процесса — не сценарий.
> 3. Параметр `force` уже есть и решает проблему тестов ровно там, где она
>    возникла.
> 4. Инъекция зависимости ради тестируемости — это лишний параметр в
>    `buildArgs`/`buildImageArgs` и в каждом вызывающем, ради сценария, который
>    в проде не случается.

## Ответ GPT

> Ты неправ в ключевом месте: кэшируется не только достоверная capability, но и
> ошибка её измерения.
>
> Реальный продакшен-сценарий без смены бинаря: первый `codex exec --help`
> завис, завершился с ошибкой или вернул обрезанный вывод. Код не проверяет
> `status`/`error`; любой непустой кусок считается `probed: true`, а пустой
> результат тоже сохраняется — в памяти и на диск с корректной версией. После
> этого неверный набор флагов живёт бессрочно, включая следующие запуски
> сервера. `force` здесь не решение: в проде некому понять, когда его вызвать.
>
> Месяцами падавший тест — прежде всего дефект изоляции тестов и контроля CI,
> не доказательство продуктового бага. Но текущая починка всё ещё хрупкая:
> сброс после assertion не находится в `finally`; при падении проверки кэш
> снова загрязнит оставшийся прогон.
>
> Твоя позиция работает только при жёстком контракте: executable не меняется до
> рестарта процесса, а первая проба гарантированно полна и успешна. Второго
> гарантировать нельзя.

## Проверка

Утверждения второй модели — не доказательство. Это проверено подстановкой
обычного `node` вместо `codex`: `node exec --help` пишет в stderr и выходит с
ненулевым кодом, то есть ведёт себя ровно как сломанный бинарь.

```
probed: true | sandbox: false | cd: false | json: false
args: ["exec","-"]
--json: ПОТЕРЯН   --sandbox: ПОТЕРЯН   --cd: ПОТЕРЯН   --skip-git-repo-check: ПОТЕРЯН
```

`buildArgs` вырождается в `["exec", "-"]`. Потеря `--cd` означает, что Codex
будет работать в каталоге процесса сервера, а не проекта — делегированная задача
правила бы не тот репозиторий. И результат записывался на диск с валидным
ключом версии, то есть переживал перезапуск.

Последствие, которое предсказал GPT, оказалось реальным. Тяжесть — больше, чем
предполагала любая из сторон.

## Исход

Пробой теперь считается только штатно завершившийся `help`, а неудачная проба
не кэшируется ни на диске, ни в памяти: следующий вызов пробует снова, а до тех
пор действует прежний запасной набор базовых флагов. Регрессия `1e` это
закрывает и идёт в том числе на Windows, в отличие от shebang-заглушки, которая
нужна остальным тестам возможностей.

Второе замечание GPT тоже верно: тест `1d` теперь сбрасывает состояние в
`finally`.

Две позиции, одна из них неверная, и вскрыло это именно несогласие. Ради этого
плагин и существует.
